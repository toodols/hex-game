# Bug audit — hex-game

Audit date: 2026-10-04. Read-only: no source files were changed. It covers the working tree as it is on disk, including the uncommitted `serialize → view` and `structures → serializing` refactor.

Confidence labels: **CONFIRMED** means the code path was traced and it definitely fires. **LIKELY** means the mechanism is clear but one step depends on runtime conditions. **SPECULATIVE** means it was not confirmed. Every finding in the top two sections, and most in the others, was re-read against the code during consolidation.

---

## ⚠️ Read this first

**A single update that can't be serialized stops the game permanently for everyone, and right now several ways to trigger that are reachable through normal play or a single remote call.** Two things combine to cause this:

1. `flush_updates` (`src/server/updates.lua:162-184`) serializes each player's batch without a pcall and only clears `world.updates_buffer` after the loop. If one update throws, it stays in the buffer, so every later flush throws as well.
2. The turn loop (`src/server/turn_scheduler_init.lua:43-50`) sets `end_time = math.huge` before it spawns `run_turn`. If anything in the action phase throws (including that flush at `action_phase/init.lua:301`), `get_end_time()` never runs. The loop thread then reaches `error "An irrecoverable error occurred"` (line 37) and dies. No later turn is ever scheduled.

The binary encoder throws on nil, on tables, on out-of-range integers (`string.pack("I1", 256)` gives "unsigned overflow"; `("i4", 8e9)` gives "integer overflow", both checked with lune), and on strings longer than 65535 bytes in `s2`.

Known triggers, with details in section 1:
- **Any player whose Roblox UserId is above 2³¹, which includes essentially every account created in the last few years.** `player_id = i32`.
- **Any exploiter**, by sending `rotate_entity` with `rotation = 256` (or a string or table), `set_recipe` with a non-string, an `ability` with a junk `coordinate`, or a malformed `update_settings`.
- **Normal play:** using Phony's disguise ability, or a game that ends in a draw.
- **Normal play:** queuing a deconstruct and an attack on the same turret in one turn, or killing a taunt on the map edge. These throw inside the action phase directly.

The client has the same single-point-of-failure shape (finding 1.9): any error in `handle_updates` freezes that player's board until they rejoin.

The fix for the amplifier is small and removes most of the blast radius: clear the buffer before serializing, pcall each player's serialize, and let the turn loop reschedule when `run_turn` errors. The individual triggers still need fixing, but they would then cost one update instead of the whole match.

## 1. Breaks the game for everyone, or lets a player cheat

### 1.1 [CRITICAL][CONFIRMED] Players with UserId above 2³¹ break the server
- **Location:** `src/shared/serializing/versions/v20260517.lua:152` (`player_id = i32`), used at :353-354 (team `players` and `historical_players`), :459/:482/:608 (`skipped`), and :462 (`player_data` map keys).
- **What goes wrong:** Roblox UserIds have been above 2,147,483,647 for years. When such a player joins, `auto_add_player` puts their id in `team.players`. From then on:
  - the "teams" update throws "integer overflow" and wedges the flush;
  - every `GetWorldData` throws, because the world view contains every team, so **no client can load**;
  - `serialize_world` (saves and the conclusion archive) throws.
- **Fix:** encode `player_id` as `f64` (or `i64`) and encode the `player_data` map keys as `str`, under a new schema version.

### 1.2 [CRITICAL][CONFIRMED] Exploiter wedges the server with one remote call (unvalidated rotation, recipe, coordinate and settings)
- **Location:**
  - `src/server/router/init.lua:86` (`entity.rotation = entry.rotation`)
  - `router/init.lua:204` (`entity.current_recipe = entry.recipe_id`)
  - `router/construct_interaction.lua:83` (rotation on construct)
  - `router/ability_interaction.lua:40-47` (the whole client `entry` is stored in `queued_decisions`, and `coordinate` is unchecked for `solution_activate`/`impression_activate`)
  - `router/init.lua:271-273` (settings; see 1.7)
- **What goes wrong:** the exploiter fires `ClientInteractionRemote` with `{{type="rotate_entity", entity_id=<own entity>, rotation=256}}`. The value is stored on the entity, and the next serialize of that entity throws (`option(u8)`). Because the bad value stays on the entity, the failure persists:
  - every flush fails, so no player receives updates;
  - every joiner's `GetWorldData` fails;
  - the next turn's flush kills the turn loop.

  The game never recovers on its own.
- **Fix:** validate every client field in the router: rotation must be an integer from 0 to 5; `recipe_id` must be a key of `config.recipes`; a coordinate must be three integers with x+y+z=0 that maps to an existing cell. Build stored decisions from validated fields instead of storing `entry`. Also fix the flush and turn-loop amplifier described above.

### 1.3 [CRITICAL][CONFIRMED] Any player can stall the game by queuing deconstruct and an attack on the same entity
- **Location:** `src/server/action_phase/init.lua:181-185`, `abilities.lua:28-30`, `systems/init.lua:66-67`
- **What goes wrong:** in one planning phase, the player clicks Attack on their turret, scout or ragnarok, then clicks Deconstruct. The router accepts both. In the action phase, `delete_deconstructed_entities` removes the entity, so `compute_systems` skips it and `entity_system_map[id]` is nil. `abilities.cannon` then calls `system_has_items(world, nil, …)`, which indexes `system.entities` and throws inside `run_action_phase`. The turn loop dies. **Two normal clicks, no exploit tools.** The same stale path also lets `solution_activate` and `disguise` fire for an entity that was deconstructed that turn.
- **Fix:** in `handle_ability_actions`, skip the action if the entity is nil, `is_destroyed` or `will_die`. Have deconstruct drop the entity's other queued decisions.

### 1.4 [CRITICAL][CONFIRMED] Phony's disguise sends update types the schema doesn't know, crashing the server and leaking the disguise
- **Location:** `src/server/abilities.lua:99-102, 123-127` emits `{type="entity_disguise", entity_id=phony, disguise_id=copy}` and `{type="disguise"}`; `src/server/updates.lua:150-151` (`else return update`) forwards unknown types to every team; the `tagged_union` in `v20260517.lua:558-631` has neither type.
- **What goes wrong:** using the disguise ability in a live game makes the flush throw "Invalid enum value", which wedges the game as above. Before serialization, those updates are also handed unfiltered to enemy teams, revealing which real entity is behind which disguise. Tests miss it because test worlds have no players, so `flush_updates` never serializes.
- **Fix:** make the fallback in `get_updates` return `nil`, and either stop emitting these updates or add filtered schema cases for them.

### 1.5 [CRITICAL][CONFIRMED] Any player's client freezes permanently on one bad update
- **Location:** `src/init/game.client.lua:27-38`
- **What goes wrong:** the drain loop sets `processing = true` and calls `handle_updates` with no pcall. Any throw leaves `processing` stuck at true. After that, every later batch is queued and never applied, so the board freezes until rejoin. Reachable throws include:
  - nil entities in `update_neighbors` (`client/game.lua:67-72`), `hide_entities` (:193) and `handle_entity_event` (:271);
  - `instance_entity_map[nil] = nil` in ragnarok `on_destroy` (`entity_impls/ragnarok.lua:53-55`);
  - unchecked instance indexes in fountain, vertex, scout, turret, stockpile, vault and torch;
  - any error in a `world_update_signal` UI listener, because `signal.send` is synchronous.

  Findings 2.2 and 2.6 give concrete sequences that reach these.
- **Fix:** run each batch through `xpcall` and always reset `processing`.

### 1.6 [CRITICAL][CONFIRMED] A taunt killed on the map edge crashes the action phase
- **Location:** `src/server/entity_impls/taunt.lua:26` passes the unfiltered `neighbors_leq(pos, 1)`; `src/server/damage/init.lua:151-154` calls `get_attackable_entities(world, nil_cell)`, which runs `for … in cell.entities`.
- **What goes wrong:** any taunt on a boundary cell that is killed (not deconstructed) throws inside the action phase, and the turn loop dies.
- **Fix:** filter targets through `world_mod.coords_filter`, or `continue` when `cell == nil` in `damage_cells`.

### 1.7 [CRITICAL][CONFIRMED] `update_settings` validates against the wrong schema: keybinds are never saved, and an exploiter can wedge the server
- **Location:** `src/shared/serializing/init.lua:74` (`validate_player_settings = main.player_data.validate`), used at `router/init.lua:271-273`.
- **What goes wrong:**
  - A real client sends `{keybinds=…}`. That fails `player_data` validation (no `rating`, among other fields), `unwrap` throws, and `catch` swallows the error. Keybind changes are only kept locally and are lost on rejoin.
  - An exploiter can instead send a full player_data-shaped table. It validates, gets stored as `settings`, and then fails to serialize as `player_settings`, wedging the flush.
- **Fix:** use `main.player_settings.validate` and build the stored settings from the validated fields only.

### 1.8 [CRITICAL][CONFIRMED] Research is shared with enemies: an enemy laboratory unlocks your blueprints
- **Location:** `src/shared/researches.lua:135-159` (the `team` parameter is never used), consumed at `src/server/action_phase/try_promote_actions.lua:59`.
- **What goes wrong:** `get_cells_researches` adds the completed research of *every* entity that influences the cell, whoever owns it. A player who never researched taunt, vault, heart, proxy or fountain places the blueprint within range 4 of an enemy Sage (or range 2 of an enemy proxy), and it promotes using the enemy's research. The build menu shows the same wrong unlocks (`buildings_frame/init.lua:162`). This is a game-balance cheat that needs no exploit tools.
- **Fix:** only count influences from `complete`, non-destroyed entities that are allied with `team`.

### 1.9 [HIGH][CONFIRMED] A taunt *blueprint* is a free shield: it forces enemy cannons onto an empty cell
- **Location:** `src/server/influences.lua:19-27` runs `influences` for every active entity, blueprints included. `src/server/entity_impls/taunt.lua:17-23` doesn't check status. `src/shared/ability.lua:32-45` doesn't check `taunt.status` or visibility.
- **What goes wrong:** a blueprint costs nothing up front, needs no research to place, and is invisible to enemies. While it exists, every enemy scout, turret or ragnarok within range 3 can only target the blueprint's cell, and `get_attackable_entities` skips blueprints, so those shots do nothing. The victim's UI shows normal targets, which the server silently rejects (`ability_interaction.lua:28-34`).
- **Fix:** in `taunt.influences` (or the taunt filter), require `status == "complete"` and visibility to the attacking team.

### 1.10 [HIGH][LIKELY] Necromancer blueprints revive allies for free
- **Location:** `src/server/entity_impls/necromancer.lua:15-68`, `action_phase/entity_event_actions.lua:45-50`
- **What goes wrong:** same root cause as 1.9. A necromancer blueprint gets allied death events and spawns graves, giving up to 4 revives per free blueprint. A necromancer already at 0 hp also keeps reviving for the rest of the turn, because `will_die` is not checked, and emits duplicate "killed" events.
- **Fix:** return early from `influences` and `on_event` unless `status == "complete"` and not `will_die`.

### 1.11 [HIGH][LIKELY] Teleport data is trusted to choose the map, the teams and the player list
- **Location:** `src/init/game.server.lua:206-240, 100-105, 139-145`
- **What goes wrong:** `GetJoinData().TeleportData` from the first player to arrive decides everything. Roblox teleport data passes through the client and is not secure (the comment at `lobby.server.lua:100` acknowledges this). A party member with an exploit can:
  - assign themselves team `"1"`/`"2"` (neutral or capturable) and take control of those entities;
  - put opponents on the spectator team;
  - choose a nonexistent map, which crashes the server;
  - list a fake UserId, so the match never starts.
- **Fix:** have the lobby publish the room server-side (MemoryStore keyed by the reserved-server access code) or sign the payload. At minimum, whitelist `map` and allow only player-team ids.

### 1.12 [HIGH][LIKELY] Off-lattice and aliased coordinates are accepted from clients
- **Location:** `src/shared/coords.lua:77-89` (`encode_coord` uses only `[1]` and `[2]`, linear packing); `router/construct_interaction.lua:34-47, 80-85` stores the client's table as `primary_coordinate`.
- **What goes wrong:** `{x, y, 999}`, or `{x-1, y+2^21, …}`, encodes to a real cell's key and passes every cell, presence and blocking check. Everything that uses all three components then sees garbage: `coords_dist` (presence, range), `into_vec3` (other clients render the building elsewhere) and `hex_line`. With large values, line of sight runs millions of iterations and then throws.
- **Fix:** add a shared `is_valid_coord` (three finite integers, sum 0, small magnitude), call it in the router, and store `cell.coordinate` rather than the client's table.

### 1.13 [HIGH][CONFIRMED] The "Activate" button (Solution/Impression) breaks all updates until the end of the turn
- **Location:** `client/ui/game/entity_information/action_buttons.lua:225-231` sends no `coordinate`; `v20260517.lua:182-188` requires `coordinate = coord`.
- **What goes wrong:** one legitimate click wedges every flush, and every `GetWorldData` for that team, until the turn clears `queued_decisions` (`action_phase/init.lua:44`). Players earlier in the `GetPlayers()` order receive the partial batch twice. A player joining in that window has their client script die, because `game.client.lua:20` has no retry.
- **Fix:** make the ability decision's coordinate `option(coord)`.

### 1.14 [HIGH][CONFIRMED] A draw can't be serialized, and conclusion throws before sending the conclusion screen
- **Location:** `v20260517.lua:440` (`winning_coalition = coalition_id`, not optional); `src/server/conclusion/init.lua:55-56` returns `true, nil`, and line 130 runs `table.find(nil, …)` on a draw in live servers.
- **What goes wrong:** when every player team dies on the same turn, the conclusion update can't be written, every later `GetWorldData` fails (because `partial_world.conclusion` is included), and in live servers the webhook code throws first. Clients never see the end screen.
- **Fix:** use `option(coalition_id)` and guard `winning_teams` for nil.

### 1.15 [HIGH][CONFIRMED] Conclusion makes unprotected HTTP and DataStore calls before it sends the conclusion update
- **Location:** `src/server/conclusion/init.lua:89` (`SetAsync`), 138 (`GetNameFromUserIdAsync`), 150 (`PostAsync`)
- **What goes wrong:** any of these can fail: Discord rate limits or a 2000-character content limit, HttpEnabled being off, or DataStore throttling. A failure aborts `handle_conclusion` before `add_update{type="conclusion"}` (line 159) and aborts the rest of the action phase. The schedule is already stopped, so the match freezes with ratings half-saved.
- **Fix:** add the conclusion update first, then pcall each save and run the webhook in `task.spawn`.

### 1.16 [HIGH][LIKELY] The world archive in the conclusion update exceeds the `s2` 64 KB limit and leaks the full world
- **Location:** `v20260517.lua:441` (`world_archive = str`, which is `s2`); `conclusion/init.lua:105-110`
- **What goes wrong:** the archive is the base64 of the entire world, including every config description, so a mid-sized game will likely pass 65535 bytes. At that point `string.pack` throws (verified), the conclusion update can't be sent, and later world views fail. Even under the limit, it ships an unfiltered world (`server_data`, enemy blueprints) to every client.
- **Fix:** keep the archive server-side, or at least use `s4` and don't replicate it.

### 1.17 [HIGH][LIKELY] Deleting the `v20260511` schema makes those saves unreadable *(uncommitted change)*
- **Location:** `src/shared/serializing/versions/init.lua`. HEAD registered `v20260511`; the working tree drops it.
- **What goes wrong:** player data saved under that version id hits `assert(version ~= nil)` in `deserialize_player_data`. `get_player_data` throws inside `task.defer`, so `world.player_data[uid]` stays nil for that player. They can't build (1.21), and conclusion's `update_ratings` throws on them.
- **Fix:** keep the old version module, with a migration, before committing the refactor.

### 1.18 [HIGH][LIKELY] The unlockable enum order is not sorted, so owned unlockables can swap between client, server and saves
- **Location:** `v20260517.lua:397` (`enum(unlockable_mod.get_unlockables())`); `src/shared/unlockable.lua:35-47` iterates `entity_mod.registry`.
- **What goes wrong:** the comment at `v20260517.lua:44-45` says registry order differs between client and server, which is why `entity_types` is sorted, but unlockables are not. Indices in `unlockables_owned` can decode to the wrong unlockable on the client. Because the same order is used in DataStore saves, adding an entity type can silently swap what players own.
- **Fix:** `table.sort` the unlockable list (and `research_id`) before building the enum.

### 1.19 [HIGH][CONFIRMED] pow: a removed permission never persists, so revoked admins come back
- **Location:** `pow/src/shared/builtins/commands/admin.lua:30-37`
- **What goes wrong:**
  - Demoting someone to `normal` returns early without saving, so their old admin entry is reloaded on the next server.
  - The first save seeds the store with `config.permissions`, so the hard-coded owners in `game.server.lua` become permanent even after they are removed from code.
- **Fix:** delete the user's entry when the new permission is `normal`, and seed a missing store with `{}`.

### 1.20 [HIGH][CONFIRMED, latent today] pow: nested commands skip the permission check
- **Location:** `pow/src/shared/runtime/init.lua:208-251` (`run_command` has no permission check)
- **What goes wrong:** only the top-level `server_run` is permission-checked. A moderator runs `bind_tool <tool> {ban @all …}` (or `{load_game …}`, `{destroy …}`), clicks the tool, and admin-only commands run on the server. A user with only the `control_flow` grant can use `server {…}` the same way. Today only owners exist, so this needs a moderator or a partial grant to exploit. **A non-admin player cannot reach any privileged command; that was verified end to end.**
- **Fix:** check the process owner's expanded permissions in `run_command` before `run_function`.

### 1.21 [MEDIUM][CONFIRMED] Unprotected player-data load leaves `player_data` nil: no building, a broken leave handler and a broken conclusion
- **Location:** `src/init/game.server.lua:167-176, 198-199`; `datastore/init.lua:48-58`; `construct_interaction.lua:59-60`
- **What goes wrong:** `get_player_data` runs in `task.defer` with no pcall. On failure, and also during the GetAsync yield itself:
  - every `construct` throws (`nil.unlockables_owned`);
  - `PlayerRemoving` asserts in `set_player_data(nil)` before `recalculate_skips`/`republish_teams`, so skip counts go stale;
  - `update_ratings` throws at conclusion.
- **Fix:** pcall with retry, fall back to defaults flagged "don't save", and guard nil.

### 1.22 [MEDIUM][CONFIRMED] Disguise has no range check
- **Location:** `src/server/router/ability_interaction.lua:35-39`
- **What goes wrong:** phony's disguise has `range = 4`, but the server only checks that the target cell exists, so a client can copy any visible entity anywhere on the map.
- **Fix:** check range, plus line of sight if it is intended.

### 1.23 [MEDIUM][LIKELY] Ability updates reveal unseen attackers
- **Location:** `src/server/updates.lua:94-110`
- **What goes wrong:** when an enemy fires on your cell, you receive its `entity_id` and `ability_id` even if you can't see it, which leaks that it exists and which entity it is. The client then hits finding 2.1.
- **Fix:** send the update only if `entity_visibility` passes for the attacker, or strip `entity_id`.

### 1.24 [MEDIUM][CONFIRMED] Rash's ability throws, because it has no range

## Latent bugs in code with no current caller
- `remove_entity` clears only the primary cell, so multi-cell entities would leave stale ids, and `query_entity` would then `error()` on them (`server/entity.lua:222-229`). Only the unbuildable, test-only `big` entity is affected.
- `signal.wait()` resumes the wrong thread (`shared/signal.lua:14-22`).
- The `cell_update` shape differs between the server, schema and client (`updates.lua:88-93`, `v20260517.lua:569`, `client/game.lua:307`).
- `datastore.update_player_data` treats the stored base64 string as a table (`datastore/init.lua:60-82`).
- `fit()` in coords is broken (`rot` is unused).
- `ai.find_closest` ignores its cell.

## Test-suite gaps that let the critical bugs through
- Test worlds have no players, so `flush_updates` never serializes, and no test exercises the wire format end to end. This is why 1.4 and 1.13 pass.
- `check_conclusion` returns false while `_G.is_testing`, so the draw path in 1.14 is never tested.
- `archive_world` (`tests/serializing.lua:126-137`) asserts nothing about the decoded world, and `fit_coords` (`tests/unit.lua:189-191`) is empty.

## Top fixes, in priority order
1. **Contain failures.** In `flush_updates`, clear the buffer first and pcall each player's serialize. In the turn loop, reschedule when `run_turn` errors. On the client, xpcall each batch and always reset `processing`. This turns every "stops the game forever" item into "one update lost".
2. **Change `player_id` to `f64`/`i64`** (1.1). Until this lands, any new-account player breaks the server.
3. **Validate every router field** (rotation, recipe_id, coordinate, settings), and build stored decisions from the validated fields (1.2, 1.7, 1.12).
4. **In `handle_ability_actions`, skip destroyed and `will_die` entities** (1.3), and **filter off-map cells in `damage_cells`** (1.6).
5. **Filter influences by owner and status**, covering research (1.8), taunt (1.9) and necromancer (1.10).
6. **Fix the schema holes:** `option(coord)` for ability decisions, `option(coalition_id)` for the conclusion winner, no replicated `world_archive`, and no forwarding of unknown update types (1.4, 1.13, 1.14, 1.16).
7. **Before committing the serializing refactor, restore the `v20260511` decoder and sort the unlockable enum** (1.17, 1.18).
